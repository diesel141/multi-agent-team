## 1. Context（文脈）

### 1.1 経緯 — TASK-0007 で顕在化した 2 つの構造的欠陥

TASK-0007「P18-P22 文言削除と下部余白の本質再設計」の途中で、次の 2 つの欠陥が明らかになった。

1. **ロール欠陥**: pptx の余白 / vertical anchor / typography に関する判断は本来「UX 仕様の確定」に該当するが、本 PJ には Designer ロールが存在せず、Tech Lead が技術判断と並行して UX 判断も担っていた。結果、Tech Lead の修正案で初回 PM 承認が出たあとに「外枠は対称だが内部要素が偏っている」見え方の不整合が発覚し、PM が承認を撤回せざるを得なくなった
2. **フロー欠陥**: ADR-0002 で「次メンバー提案の上限 3 職種」（BE / FE / SRE）に Designer は入っておらず、却下案 A〜G にも Designer は登場しない（**見落としドメイン**）。緊急対応として PM 神崎が `docs/persona.md` §5.3 「PM がペルソナ自体は自分で起こしたい場合は分担を変更可能」の **例外条項** を適用し `docs/personas/ui_ux_designer.md`（白井美雪）を直接起案・召喚、Designer 案で再修正を完遂した

### 1.2 2026-04-27 ユーザー回答による権限境界の確定

TASK-0008 着手前のユーザー回答（2026-04-27）により、本 PJ の権限境界が明示的に確定した:

- **ペルソナ追加（人材起案）は PM の仕事**（=正規ルート）
- **PR レビューとマージは Tech Lead の仕事**（=正規ルート / PM はマージしない）

この確定により、TASK-0007 で PM が Designer ペルソナを直接起案したことは「例外条項の適用」ではなく「正規ルートの先行実施」となる。ADR-0002 §5.3 の「ペルソナ起案は Tech Lead 起案 + PM 承認」前提は **古い前提** となり、正規ルートを書き直す必要が生じた。

### 1.3 本 ADR の性質

当初の TASK-0008 開始指令では本 ADR は「事後追認 ADR」として起案される予定だったが、§1.2 の権限境界確定により **枠組みを書き換える構造改善 ADR** に昇格する。本 ADR は ADR-0002 §5.3 を **Superseded（部分上書き）** し、以下を確定する:

- ペルソナ起案フローの新規律（PM 起案を正規ルート、Tech Lead 起案を残置ルートとして両立）
- UI/UX Designer の役割と他ロールとの境界
- ADR-0002 で見落とされたドメイン候補の点検結果

なお、ADR-0002 のうち BE/FE/SRE 採用順（§2.1）は本 ADR では変更しない。継続有効。

## 2. Decision（決定）

### 2.1 決定 1: 権限境界の正規ルート化

| 領域 | 担当 | 決定権 | 補足 |
|------|------|--------|------|
| **人材ペルソナ起案**（新ロール追加） | **PM** | 起案 + 採択 | Tech Lead からの提案も受けるが、最終的なペルソナ確定は PM |
| 技術ペルソナの **スキル要件 / 初期タスク定義** | Tech Lead | 起案 | PM が承認 |
| 通信プロトコル / 受入基準 / スコープ / 期日 | PM | 確定 | 既定どおり |
| 技術スタック / アーキテクチャ判断 | Tech Lead | 確定 | ADR で残す |
| **PR レビューとマージ** | **Tech Lead** | 確定 | PM はマージしない（Designer / BE / FE / SRE 等の PR も Tech Lead が捌く） |
| UX 仕様（padding / vertical anchor / typography / grid） | Designer | 確定 | PM が裁量で UX 数値を確定したら Designer が差し戻す |

**ADR-0002 §5.3 との関係**:
- ADR-0002 §5.3 では「ペルソナ起案は Tech Lead 起案 + PM 承認、PM がペルソナを起こすのは例外（分担変更可能）」と書かれていた
- 本 ADR §2.1 で **正規ルートを「PM 起案」に格上げ**。Tech Lead 起案ルートは §5.2 に残す
- ADR-0002 §2.1 の BE/FE/SRE 採用順は影響を受けない（§5.3 の「起案主体」だけが本 ADR で書き換わる）

### 2.2 決定 2: UI/UX Designer ペルソナ採択

`docs/personas/ui_ux_designer.md`（白井美雪）を本 ADR で正式採択する。TASK-0007 後半 / TASK-0009 で実装＆実証済。

| 項目 | 内容 |
|------|------|
| 役割 | UX 仕様の最終決定者（padding / vertical anchor / typography / grid / color system） |
| 主成果物 | 視覚仕様書（数値 + 実描画 PDF）/ Squint test 結果 / 受入チェックリスト適用結果 |
| 起用形態 | タスク起点（pptx / 印刷物 / Web UI など視覚仕様が要所のタスクで召喚）|
| Tech Lead との境界 | Designer = 視覚仕様の確定 / Tech Lead = コード実装の品質保証・PR レビュー＆マージ。境界曖昧時は **議論（informal）** で言語化してから分業 |
| PM との境界 | PM = スコープ / 期日 / 受入基準 / 受入判定。PM が UX 数値を裁量確定したら Designer が即座に差し戻す権限を持つ |

### 2.3 決定 3: 見落としドメイン候補リスト

ADR-0002 §3 の却下案再評価（本 ADR §3）に基づき、現時点では起用しないが将来の起用可能性が高い職種を **見落としドメイン候補** として §4 にリスト化する。各候補に「適用トリガー」と「再考閾値」を明示し、ADR-0002 の上限 3 職種制約には組み込まない（見落とし候補は予備リスト扱い）。

### 3.1 構造的原因の分析: なぜ Designer は ADR-0002 で見落とされたか

ADR-0002 §1.2 の「直近 4-8 週間で発生する見立て」は **「コードを書く / インフラを作る」職能だけ** を想定しており、「視覚仕様を確定する」職能の必要性が見えていなかった。具体的には:

1. **Conway's Law の適用が技術構造に偏っていた** — `docs/adr/0002-next-team-members.md` §1.3 で Conway's Law を引用したが、適用対象が「通信レイヤ実装メンバー不在」だけで、視覚レイヤ実装メンバー不在は意識されていなかった
2. **「研修資料生成」タスクの解像度が低かった** — ADR-0001 / ADR-0002 起案時は「pptx を python-pptx で生成する」程度の認識で、padding / vertical anchor / typography が要所になる前提が抜けていた
3. **Designer が ADR-0002 §3 却下案にすら登場しなかった** — 検討対象から完全に抜け落ちており、これが本 ADR §4 の「見落としドメイン候補リスト」を恒久化する直接の動機

### 3.2 再発防止: 見落としドメイン候補リスト（§4）の維持

ADR-0002 当時の検討範囲は「コードを書く職能」中心だった。今後新ロールを起案する際は、本 ADR §4 のリストを起点に「想定外ドメインが残っていないか」を必ず点検する。Tech Lead は ADR 起案時、PM は半年に 1 度のリスト棚卸しでこれを担保する（§6-3 開いている論点）。

## 4. 見落としドメイン候補（予備リスト）

ADR-0002 上限 3 職種制約には組み込まないが、適用トリガーが揃った時点で正規ルート（PM 起案）にて起案する。**各候補に適用トリガー + 再考閾値を明示**。

### 4-1: Technical Writer / Editor

- **役割**: 研修資料の言い回し統一、用語集メンテ、外部公開ドキュメントの編集
- **適用トリガー**: 外部公開前提の研修資料 / 顧客向け技術ドキュメントが 3 件以上同時並行で動く、または用語集の収録語数が 100 件を超える
- **再考閾値**: 上記いずれかに到達した時点 / または PM/Designer から「テキスト編集に追われて本来業務が滞る」フィードバックが 2 回以上出た時点
- **起用しない理由（現時点）**: 用語集は機械生成 + Designer 視覚レビューで十分捌けている。Tech Lead レビューでテキスト品質も担保中

### 4-2: Data Engineer / Analytics Engineer

- **役割**: 通信レイヤ（Notion 掲示板 / 歴史化）から派生するデータ分析、Notion DB スキーマ変遷追跡、KPI ダッシュボード構築
- **適用トリガー**: タスク件数が累計 50 を超える、または「歴史化メモから組織学習を抽出する」分析タスクが PM から発出される
- **再考閾値**: TASK 累計 50 件到達 / 月次タスク発出が 10 件超で 3 ヶ月連続 / 歴史化アーカイブから機械的にインサイトを取り出す要求が出た時点
- **起用しない理由（現時点）**: 現在の歴史化アーカイブは数十ページ規模で、PM 神崎が直接読み込んで判断材料化できる量

### 4-3: Security Engineer

- **役割**: シークレット管理レビュー、依存パッケージ脆弱性監査、Notion / Vercel / Supabase などの権限境界レビュー、外部公開物のプライバシー監査
- **適用トリガー**: 外部公開 Web サービスを 1 つでもデプロイ、または PII / 認証情報を扱うサブリポが発生
- **再考閾値**: 本番デプロイ 1 件目 / 認証導線をプロダクションに乗せる時点 / SaaS 月額 $200 超（ADR-0002 §2.2 SRE トリガと連動）
- **起用しない理由（現時点）**: 本リポは社内向けドキュメント中心で外部公開なし。`.env` 集中管理で初期は十分

### 4-4: Localization / i18n Specialist

- **役割**: 多言語化（英語 / 中国語 / 韓国語等）対応の翻訳監修と用語集メンテ
- **適用トリガー**: 多言語版の研修資料発注、または英語圏ユーザーへの公開
- **再考閾値**: 多言語タスクが 1 件発出された時点 / 英語版 pptx の納品要件が確定した時点
- **起用しない理由（現時点）**: 現在のターゲットは日本語話者のみ

### 4-5: Product Designer（情報設計 / IA 寄り）

- **役割**: Web UI / アプリの情報設計、ユーザーフロー設計、ワイヤーフレーム
- **適用トリガー**: Web UI / モバイルアプリのプロダクト開発タスクが発出される
- **再考閾値**: Web UI を含む開始指令が発行された時点（ADR-0002 §2.2 FE トリガと連動）
- **起用しない理由（現時点）**: Designer 白井美雪はビジュアル / プレゼンテーション特化のため UI 設計までは守備範囲外。ただし当面はアプリ開発タスクが見えていないため Product Designer の即時起用は不要。FE 起用と同時に検討する

## 5. ペルソナ起案フローの規律明文化

### 5.1 通常ルート（新規律 / 2026-04-27 確定）

```
PM 神崎が必要性を判断
   ↓
PM が `docs/personas/<role>.md` を起案
   ↓
ADR-NNNN として正式採択（PM が起案、Tech Lead がレビュー、最終決裁は PM）
   ↓
Notion 掲示板に開始指令を投下、対象ロールを起動
```

**根拠**: 2026-04-27 ユーザー回答により「人材ペルソナ追加は PM の仕事」として正規ルート化された。PM はスコープ / 期日 / 受入基準を握っており、必要なロールを最も早く検知できる立場である。

### 5.2 残置ルート（旧 ADR-0002 §5.3 ルートを縮退）

```
Tech Lead 早瀬がスキル要件・初期タスク定義を起案
   ↓
PM 神崎が承認（採否判定）
   ↓
ADR-NNNN として正式採択
   ↓
Notion 掲示板に開始指令を投下
```

**適用条件**: 案件単位で PM と Tech Lead が事前合意した場合のみ。既定は §5.1 の PM 起案ルートを使う。Tech Lead 起案ルートは「技術職能（BE / FE / SRE / Mobile / QA など）でスキル要件の言語化が PM 単独では困難」と PM が判断した場合のフォールバック。

### 5.3 起案者の選び方ガイド

| ペルソナ性質 | 推奨起案者 | 例 |
|-------------|-----------|---|
| PM 領域に近い職能（コミュニケーション / 概念設計 / 視覚仕様 / 編集） | PM | Designer / Technical Writer / PM Assistant 系 |
| 技術専門性が PM の守備範囲外 | Tech Lead 起案を相談 | Backend / SRE / Security / Data Engineer |
| 緊急性が高い（タスクブロッカー） | PM 直接起案で時間短縮 | TASK-0007 Designer ケース |

### 5.4 ペルソナファイル雛形

すべてのペルソナファイルは `docs/personas/tech_lead.md` のセクション構成を踏襲する:

1. 基本情報 / 2. 経歴 / 3. 強み・専門領域 / 4. 性格・行動原理 / 5. 責任範囲（権限境界）/ 6. 主な成果物 / 7. プロトコル接続（Notion 7 種メッセージ / teammate 優先 / 歴史化への寄与）/ 8. 思考フレームワーク / 9. アンチパターン / 10. コミュニケーションスタイル

PM / Tech Lead いずれが起案する場合も雛形遵守は必須。

## 6. 開いている論点（PM 議論で動かしたい点）

> 「**強い意見を弱い保持で**」。以下は本 ADR の確定後も議論で動く可能性のある点を明示する。

1. **Designer の責務と FE Engineer の境界** — FE 起用時、CSS / Tailwind を書くのは FE だが、デザイントークン（color / typography / spacing scale）の確定は Designer。FE が CSS を書く際、どの粒度から Designer の関与が必要かは未確定。Web UI タスク到来時に FE と Designer の双方を Notion 議論で言語化する想定。**※ ADR-0007 §2.1 で決議（数値仕様 = Designer / コンポーネント実装 = FE / UX フィードバックは共同議論）**
2. **ペルソナ追加ペースの上限** — ADR-0002 §1.1 では「上限 3 職種」を PM 意思決定負荷の観点で設定。Designer 採択（本 ADR）で実質 4 職種になり、§4 の見落とし候補が起用に転じればさらに増える。上限を「常駐 3 + タスク起点起用 N」に再定義するかは別 ADR 候補。**※ ADR-0007 §2.2 で決議（同時進行中 P1 タスク数 + 1 のソフト基準 + 代替不能職種は独立起用可）**
3. **見落としドメイン候補リストの棚卸し頻度** — §4 のリストは陳腐化しうる。半年ごとに PM + Tech Lead で点検する運用にするか、ADR 起案時に必ず参照する運用にするか、運用方法を確定する必要がある
4. **PM 起案ペルソナのレビュー責任** — PM が起案したペルソナを Tech Lead が技術観点でレビューする際、Tech Lead 側に「却下」する権限はあるか。本 ADR §2.1 では PM 最終決裁としているが、Tech Lead が技術整合性で異議を唱える経路は議論の余地あり。**※ ADR-0007 §2.3 で決議（採択前 Tech Lead レビュー必須 / 観点 = 責任範囲の ADR 整合性 + 技術スキルセット過不足）**
5. **§5.2 残置ルートの将来廃止可否** — Tech Lead 起案ルートを完全に廃止するか、フォールバックとして残すかは PM の運用方針次第。当面は残置とするが、今後 1 年で PM 起案 100% 運用が回るなら廃止候補

## 7. Consequences（帰結）

### 7.1 ポジティブ

1. **権限境界が明文化** — PM / Tech Lead / Designer の責任分担が ADR レベルで確定し、TASK-0007 のような「PM が UX 数値を裁量確定したが Designer が差し戻し」のような越権是正が制度化される
2. **見落としドメインの再発防止** — §4 のリストと §3.2 の点検プロセスにより、ADR-0002 同様の「検討対象から完全に抜け落ちる」事態を予防できる
3. **PM 起案ルートの正規化** — 緊急時の例外発動ではなく、平時から PM が必要なペルソナを起案できる体制になる。Tech Lead はスキル要件支援に集中できる
4. **Designer 採択が ADR で残る** — TASK-0007 後半の Designer 召喚を歴史化メモだけでなく ADR で正式採択することで、後続タスクから「Designer はいる前提」で受入基準を書ける

### 7.2 ネガティブ・リスク

1. **PM ボトルネック化リスク** — 全ペルソナ起案を PM 単独に集中させると PM の判断負荷が増える。**緩和策**: §5.2 Tech Lead 起案ルートを残置 / §5.3 起案者の選び方ガイドで分業
2. **見落とし候補リスト（§4）の陳腐化** — リストを書きっぱなしで使われない可能性。**緩和策**: §6-3 で棚卸し頻度を開いている論点に
3. **§4 の閾値が甘い可能性** — 各候補の再考閾値が「現時点での想定」に依存。実運用で閾値が早すぎ / 遅すぎ判明する可能性あり。**緩和策**: ADR 改訂を躊躇せず、運用観測で閾値を更新する
