## 1. Context（文脈）

### 1.1 経緯

本プロジェクトは初期セッション（2026-04-25）で PM 神崎が `CLAUDE.md` §1.3 / `docs/persona.md` §5.1 に **「Notion 掲示板に投稿する業務通信は 3 種メッセージ（開始指令 / 問題報告 / 完了報告）のみ」** と規律化した。設計動機は次の 3 点である:

1. **タスクのトレーサビリティ確保** — 1 タスク = 1 開始指令 = 1 完了報告で受入基準を必ず照合する
2. **歴史化の単位の純度** — 雑談ノイズが歴史化メモに混入しない
3. **沈黙によるリスク隠蔽の防止** — 問題報告を独立した一級メッセージにし、ブロッカーを早期に表面化する

しかし TASK-0001〜0004 で実務運用した結果、以下の **哲学衝突** が顕在化した。

### 1.2 ユーザー初期想定とのギャップ

ユーザー（プロジェクトオーナー）の初期想定は、次のような **流れる業務チャネル形式** だった:

```
PM: TASK-XXXX 着手してください  →  受領者: 了解、これから着手します
                                   → ある程度進んだら進捗を共有します
                                   → 不明点が出たら質問します
                                   → 完了したら成果物リンクを共有します
```

つまり Slack / IM 的な **指示 → 着手返答 → 作業報告（途中含む）** のフロー型。これに対し、3 種限定運用は **タスクカンバン的な構造**（チケット起票 → 完了報告までの間は沈黙）に振れていた。

### 1.3 TASK-0001〜0004 で観測された実証

| タスク | 観測事項 | 哲学衝突の現れ |
|--------|---------|---------------|
| TASK-0001 | Tech Lead 起用と ADR 起案。開始指令と完了報告の往復は機能した | 完了報告に至るまで Tech Lead 側の状態（受領済み / 進行中 / ブロック気味）が掲示板に現れず、PM が能動的に Notion を覗かない限り進捗不明 |
| TASK-0002 | BE ペルソナ + 通知レイヤ ADR を中断（TASK-0003 の P0 割り込みのため） | 「中断します」を伝える正規メッセージ種別が無く、ステータス更新のみで暗黙的に処理 |
| TASK-0003 | 用語集に Claude Code 用語を追加 | サンドボックス権限拒否の問題報告は機能。一方で「これから着手します」を投げる場が無く、ユーザーから「速攻なのにカンバン作業で 6 分」「着手返答が投稿できない」との指摘 |
| TASK-0004 | 用語集のカテゴリ順序変更 | 設計判断の中間共有（カラー選定理由など）を残す場が無く、結局完了報告に詰め込む形になった |

### 1.4 ユーザー判断（採択済）

ユーザーは 2026-04-26 セッションで **案 C ハイブリッド型** の採用を決裁した。本 ADR はその実装方針を確定するもの。

- **formal**: 開始指令 / 問題報告 / 完了報告（現状継続。必須項目維持）
- **informal**: 着手返答 / 進捗共有 / 質疑応答 / 議論（自由投稿を許容）

### 1.5 設計原則の再確認

`docs/personas/tech_lead.md` §4 / `docs/persona.md` §4 より:

- **Working software over comprehensive documentation** — 仕組みは動いてナンボ
- **明示性** — 暗黙知を残さない（PM 神崎）
- **意思決定の速さ** — 70% の情報で決断（PM 神崎）

3 種限定はトレーサビリティと歴史化の純度を守ったが、**チームの心理的安全と意思決定の速度を犠牲** にしていた。本 ADR はその是正である。

## 2. Decision（決定）

### 2.1 採用案: ハイブリッド型（案 C）

> **※ 部分 Superseded by ADR-0009 §2.1**: informal を 4 種から 5 種に拡張（雑談を追加）。詳細は ADR-0009 §6.1。

**Notion 掲示板を 2 層に分けて運用する。**

| 層 | 種別 | 必須項目 | 歴史化対象 | 投稿の重さ |
|----|------|---------|-----------|-----------|
| **formal** | 開始指令 | タスクID / 受領者 / 背景 / 成果物定義 / 期日 / 受入基準 / 依存関係 | ✓（要所） | 重い（規律維持） |
| **formal** | 問題報告 | タスクID / 事実 / 影響範囲 / 想定原因 / 必要な支援 / 期日影響 | ✓（要所） | 重い（規律維持） |
| **formal** | 完了報告 | タスクID / 成果物リンク / 受入基準の照合結果 / 残課題 / 学び | ✓（要所） | 重い（規律維持） |
| **informal** | 着手返答 | タスクID / 親タスクID（= 開始指令） | △（必要時に昇格） | 軽い（自由文体可） |
| **informal** | 進捗共有 | タスクID / 親タスクID | △ | 軽い |
| **informal** | 質疑応答 | タスクID / 親タスクID | △ | 軽い |
| **informal** | 議論 | タスクID（無関係なら空可） | △ | 軽い |

### 2.2 informal 4 種の用途定義

> **※ 部分 Superseded by ADR-0009 §2.3**: 進捗共有の「ログ単位禁止」制約を撤廃。詳細は ADR-0009 §6.2。

- **着手返答**: 開始指令を受領した直後の「了解、着手します」相当。SLA は 30 分以内（PM ペルソナ §5.3 の問題報告 SLA と並行）。
- **進捗共有**: 中間状態の更新。「30% 完了」のようなログ単位ではなく、「設計の方針を A から B に変えた」「テスト 1 件を残してロジック実装完了」など **判断や状態遷移の単位** で投稿する。 **（ADR-0009 §2.3 で撤廃: ログ単位投稿も許容）**
- **質疑応答**: 仕様の不確実性を解消するための問い。問題報告ほど深刻ではないが回答が必要なもの。
- **議論**: 複数の選択肢の比較・トレードオフの言語化。後から ADR に昇格する候補のソース。

### 2.3 formal は現状維持

formal 3 種は **必須項目・テンプレート・命名規約をすべて維持** する。受入基準の照合・歴史化・pptx レポートの一次ソースは formal を中心に組み立てる方針を変えない。

### 2.4 informal の自由度

- 文体: 敬体・常体どちらでも可
- 長さ: 1 行〜数百行、絵文字使用も可（ただしコミットメッセージや ADR 等の formal 文書では引き続き不使用）
- スレッド構造: Notion ページのコメント機能ではなく、独立ページ（種別 = informal の 4 種いずれか）として投稿する（理由は §5 開いている論点 1 で議論を残すが、当面の暫定）

### 2.5 ステータス遷移への影響

ステータスのモデル（`未着手 / 進行中 / ブロック / 完了 / 却下`）は変更しない。**「着手返答」を投稿した時点で受領者は親タスクのステータスを `未着手 → 進行中` に遷移させる** ことを慣行化する。これにより掲示板の状態と DB 上のステータスが乖離しにくい。

## 3. Consequences（帰結）

### 3.1 「種別」プロパティの拡張方針 — 計量比較

informal 投稿を掲示板に乗せるためのスキーマ変更には 2 案がある。本 ADR は **案 (a) 新オプション追加（種別必須は維持）** を推奨する。

| 軸 | 案 (a) 新オプション 4 種を追加 | 案 (b) 「種別」を任意化（無種別を許容） |
|----|---------------------------|-----------------------------------------|
| **DB スキーマ整合性** | 全ページが種別を持つ。フィルタ・ソート・グルーピングが可能 | 種別なしページが混在。フィルタ設計が複雑化 |
| **投稿コスト（informal 1 件あたり）** | 1 操作（4 択から 1 つ選ぶ）。1〜2 秒 | 0 操作（種別を空にする）。0 秒 |
| **PM 受入照合のノイズ排除** | 「formal のみ」ビューを 1 フィルタで作れる | 「種別が空でないもの」では完全に排除できない（informal が混入し得る） |
| **歴史化トリアージ** | 後から「議論」を grep で抽出して ADR 昇格判定が可能 | 種別なしから内容判定が必要、ヒューマンコスト増 |
| **将来の拡張性** | 必要なら種別を増減できる（中央集権的に管理） | option 設計が緩む。新種別を作る/作らないの判断軸が消える |
| **オペレーション学習コスト** | 4 択を覚える必要がある。1 セッションで定着する量 | 任意化のルール（いつ種別を付けるか）の判断が個人に依存 |

**判定**: 投稿コスト差は 1〜2 秒 vs 0 秒で実質無視できる。一方で、フィルタ可能性・歴史化トリアージ・将来拡張性のいずれも案 (a) が優位。**案 (a) を採用** する。

### 3.2 PM 神崎の日常オペレーション

- **朝会（09:00 JST）**: 「formal のみ」フィルタで未応答の問題報告と未受領の開始指令を確認。informal はスクロール参照に留め、即応の必要がある質疑応答だけピックアップ
- **受入レビュー（17:00 JST）**: 完了報告のみを対象とする。informal の進捗共有は受入基準の根拠として参照する程度
- **歴史化（18:00 JST）**: formal 3 種を必ず確認 + informal の中で「ADR 候補」「失敗と学び」「重要な制約」に該当しそうなものを選択して `docs/history/` に転記

### 3.3 Tech Lead 早瀬の日常オペレーション

- **開始指令受領時**: 着手返答を即時投稿（30 分以内）→ ステータス `未着手 → 進行中`
- **設計判断の途中**: 議論で選択肢を言語化（後から ADR §3 Considered Alternatives へ転用しやすい形で）
- **不確実性検知時**: 質疑応答で軽量に問い、回答が「業務継続に支障」レベルになった時点で問題報告へ昇格
- **完了報告投稿後**: 受入レビューで指摘が来た場合は質疑応答で対応、再オープン相当の修正が要れば新規完了報告を投稿

### 3.4 歴史化への影響

- **要所判定基準（PM ペルソナ §7）は不変**。informal は基本的に歴史化対象外、ただし「議論」で重要な意思決定が成立した場合は歴史化メモに昇格させる（昇格トリガーは §5 開いている論点 2 で議論）
- **ノイズ流入リスク**: 進捗共有や質疑応答が増えると掲示板自体は賑やかになるが、「formal のみ」フィルタが機能する限り PM の受入規律は崩れない

### 3.5 影響範囲

| 対象 | 変更内容 |
|------|---------|
| `CLAUDE.md` §1.3 | 3 種限定文言を formal/informal の 2 層構造に書き換え。formal の必須項目は不変、informal の用途定義を追加 |
| `docs/persona.md` §5.1 | 同上の表を改訂 |
| `docs/personas/tech_lead.md` §7.1 | 「シーン × メッセージ種別」表を informal 含む 8 行に拡張 |
| `docs/notion-board-schema.md` §1.3 / §2 / §4 | 「種別」 select に 4 オプション追加。本文テンプレ §2 に informal 4 種を追加。投稿タイミング §4.3 を改訂 |
| Notion DB 実体 | select option 追加実装は **PM 後追い**（Tech Lead は触らない） |

### 3.6 ポジティブ

1. **着手返答の場が公式に確保される** — TASK-0003 で発生した「速攻なのにカンバン作業で 6 分」型の摩擦が解消
2. **議論の言語化が進む** — 設計判断の途中思考が掲示板に残るため、後の ADR 起案コストが下がる
3. **トレーサビリティは維持** — formal の必須項目を不変としたため、受入照合と歴史化の規律は崩れない
4. **psmux ペイン分割との整合** — 現状の物理レイアウト（PM ペイン / Tech Lead ペイン）を変えずに、通信レイヤだけを 2 層化できる

### 3.7 ネガティブ・リスク

1. **掲示板のノイズ増加** — informal 投稿が形骸化して「進捗共有」だけが大量に流れるリスク
   - **緩和策**: §2.2 で「ログ単位ではなく判断・状態遷移の単位」と明示。違反は PM が指摘 **（※ Superseded by ADR-0009 §2.3 / §2.5: ログ単位制約は撤廃され、ロールバック閾値は「掲示板全投稿の 70% 超」に再定義。詳細は ADR-0009 §6.3）**
2. **formal/informal の境界判断ミス** — 質疑応答のつもりが実は問題報告レベル、を取り違える
   - **緩和策**: §2.2 と §3.3 に判定軸（業務継続に支障の有無）を明記。迷ったら問題報告へ昇格
3. **historization の手間増** — informal を毎日トリアージする工数が PM に発生
   - **緩和策**: PM ペルソナ §10 の 18:00 リチュアルに既に組み込まれており、増分は数分単位の想定
4. **Notion DB スキーマ追加実装の遅延** — PR マージ後 PM が select option を追加するまで informal 投稿は技術的に不能
   - **緩和策**: PR レビュー承認直後に PM が後追いで反映する運用（TASK-0003/0004 と同パターン）

## 4. Considered Alternatives（却下した代替案）

### 却下 A: 現状維持（カンバンのまま、3 種限定）

- **却下理由 1**: TASK-0001〜0004 で実証された通り、着手返答・中間判断・軽量質疑が表現できず、ユーザーから重さの指摘を受けた。哲学衝突を放置する選択
- **却下理由 2**: 「Working software over comprehensive documentation」原則に反する。規律のためのドキュメント追加が、チームの実働速度を削いでいた
- **再考の閾値**:
  - ハイブリッド運用後 **2 週間で** informal 投稿のうち「ノイズ判定」が 50% を超える（= ログ単位の進捗が大量流入し formal 受入照合に支障が出る）場合
  - または PM の歴史化トリアージ工数が **18:00 リチュアルで 30 分超** に常態化した場合
  - いずれかが発生した場合は本 ADR を改訂し、3 種限定へ回帰または進捗共有のみ撤廃する

### 却下 B: 全面フロー化（3 種を撤廃し自由投稿のみ）

- **却下理由 1**: トレーサビリティの基盤が崩れる。受入基準の照合・歴史化の単位が不明瞭になる
- **却下理由 2**: 問題報告の「30 分以内一次応答」(PM §5.3) のような規律が機能しなくなる
- **却下理由 3**: pptx レポート（CLAUDE.md §3.3）の一次ソースが粉砕される
- **再考の閾値**:
  - 開始指令 / 完了報告のトレーサビリティが低下し、受入照合コストがセッションあたり **30 分超** に増えた場合
  - または、formal 3 種の投稿率が全投稿の **20% 未満** に低下し、informal が支配的になっている場合
  - いずれかが発生した場合は本 ADR を改訂し、formal 必須項目を一部緩和して fluid 化する

### 却下 C: formal/informal を別 DB に分離

- **却下理由 1**: PM が掲示板を一望するためには 2 つの DB を行き来する必要があり、朝会のオペレーションコストが増える
- **却下理由 2**: タスクID で紐づける場合、cross-DB の relation 設定が必要になり、Notion スキーマの保守コストが上がる
- **却下理由 3**: pptx レポートの集計対象が複数になり集約スクリプトが複雑化
- **再考の閾値**: 単一 DB の総ページ数が **500 件超** になり Notion の検索パフォーマンスが体感で劣化した場合

### 却下 D: 種別はそのままで、Notion ページのコメント機能で informal を吸収

- **却下理由 1**: formal ポストに付随する形で議論が埋もれ、横断検索（タスク横断のテーマ単位）ができない
- **却下理由 2**: 親タスクが完了 / 却下されると関連議論ごと埋葬されてしまう
- **却下理由 3**: 「議論」種別を独立ページにすることで後から ADR へ昇格しやすい（コメントから ADR への転記は手間）
- **再考の閾値**: informal の投稿頻度が **タスクあたり 5 件未満** に収束し、独立ページとしての可読性メリットが薄れた場合

### 却下 E: 「種別」プロパティを任意化（§3.1 案 (b)）

- **却下理由**: §3.1 の計量比較で示した通り、投稿コスト差は 1〜2 秒に過ぎず、フィルタ可能性・歴史化トリアージ・将来拡張性のいずれも案 (a) に劣後する
- **再考の閾値**: 4 オプションの選択判断が **3 セッション連続で誤分類** され、PM が再分類する手間が顕在化した場合（任意化 + 後付け分類運用に切り替え）

### 却下 F: 質疑応答と議論を「議論」に統合（informal を 3 種に圧縮）

- **却下理由 1**: 質疑応答は「定義済みの不確実性に対する一問一答」であり、議論（複数選択肢の比較）と SLA・回答品質の期待値が異なる
- **却下理由 2**: Tech Lead 視点で「これは仕様確認だから即答してほしい」と「これは設計議論だから時間かけて考えてほしい」を区別できる方が、PM/Tech Lead の認知負荷が下がる
- **再考の閾値**: 運用 1 ヶ月で「質疑応答」と「議論」の境界判定が **5 件以上で曖昧化** した場合（区別の意味が薄いと判明したら統合）

## 5. 開いている論点（PM 承認・議論で動かしたい点）

> 「**強い意見を弱い保持で**」。本 ADR は採用案を確定するが、各論には議論余地がある。

### 5.1 informal をコメント機能で賄うか / 独立ページにするか

本 ADR §2.4 は当面「独立ページ」を推奨したが、Notion のページコメント / discussion 機能を併用する余地がある。

- 独立ページ: 横断検索容易、ADR 昇格しやすい。掲示板が長くなる
- コメント: 親 formal ポストに紐づき可読性高い。横断検索弱い、親が削除/却下されると消失

**判断のための実証**: ハイブリッド運用 1 週間後に「議論」種別のページが 5 件以上溜まったら、横断利用パターンを観察してこの論点を再決裁。

### 5.2 議論 → ADR / 歴史化メモへの昇格トリガー

informal の「議論」が後から ADR や歴史化メモに昇格すべき要所を含む場合の昇格ルールが未定義。候補:

- (i) Notion のスター / pin プロパティを追加し、PM/Tech Lead いずれかが pin した議論は週次で ADR 起案候補として棚卸し
- (ii) 議論ページに「昇格候補」チェックボックスを追加し、起案者自身が flag を立てる
- (iii) 運用ルールのみ（プロパティ追加なし、PM が 18:00 リチュアルで判定）

最も軽量な (iii) を当面の暫定とするが、PM の判定漏れが顕在化したら (i)(ii) を導入する。

### 5.3 受領者・発信者プロパティの粒度調整

informal の「議論」は特定受領者を持たない場合がある（チーム全体への投げかけ）。スキーマ上どう扱うか:

- (a) 受領者を `Team`（全員）という擬似値で表現
- (b) 受領者を任意化（種別が議論の場合のみ）
- (c) 議論用に別の関係プロパティ（multi-select）を導入

最も影響範囲が小さい (b) を推奨するが、本 ADR では決め切らず、初回の「議論」投稿時に判断する。

### 5.4 進捗共有の頻度上限

> **※ Superseded by ADR-0009 §2.3 / §6.4**: 候補 (iii) を採択し本論点クローズ。ノイズ流入時は ADR-0009 §3 却下 (b) のタスク日次上限導入を再検討。

「30% 完了」のような細かすぎるログを抑止する規律をどこまで明文化するか。候補:

- (i) タスクあたり進捗共有上限 3 件 / 日（緩い上限）
- (ii) 「判断や状態遷移の単位で投稿」という運用原則のみ（§2.2 で記載済）
- (iii) 上限なし、ノイズ判定は PM の事後フィードバックに委ねる

(ii) を本 ADR で採用したが、ノイズ流入が観測されたら (i) を導入する。 **（ADR-0009 §2.3 / §6.4 で (iii) に変更）**

### 5.5 着手返答の SLA と未投稿時の扱い

「着手返答 30 分以内」を §2.2 で明示したが、次の点が未確定:

- 30 分超過した場合のエスカレーション（PM が問題報告を立てるか、催促のみか）
- Tech Lead が物理的に不在（別タスク中）の場合の扱い
- 着手返答なしで完了報告に直行した場合（タスクが極めて短時間で終わった場合）の許容

当面は「30 分は努力目標、未投稿は PM が口頭で催促」とする。問題が顕在化したら別 ADR を起案。
