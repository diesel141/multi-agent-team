## 1. Context（文脈）

ADR-0006（ペルソナ起案フロー規律と職能見直し）と ADR-0003（通知レイヤ実装方式）の起案を経て、複数 ADR の §「開いている論点」に **PM 判断を要する組織規律論点** が累積した。BE 久遠周採択完了 + FE 起用判断接近 という節目に、これらを 1 ADR にまとめて正式化する。

### 1.1 統合対象の論点（5 件）

| # | 出典 | 論点 | 既決状況 |
|---|------|------|---------|
| 1 | ADR-0006 §6 (1) | Designer × FE の境界 | 未決 |
| 2 | ADR-0006 §6 (2) | ADR-0002 §1.1 上限 3 職種の見直し | 未決（Designer 採択で実質 4 職種化） |
| 3 | ADR-0006 §6 (4) | PM 起案ペルソナへの Tech Lead レビュー権限 | TASK-0011 で運用試行 → 採用方向で決着 |
| 4 | ADR-0003 §6 (4) | `multi-agent-template` 起票タイミング | TASK-0002 受入で「後追い派」採用済 |
| 5 | ADR-0003 §6 (6) | send-keys 「通知のみ」規律の CI 自動検証 | 別 ADR 候補として保留方向 |

論点 (1)(2) は新規採用案決定。(3)(4)(5) は既決方針の正式化。

### 1.2 統合する理由

- BE 着任直前 / FE 起用判断接近のタイミングで **組織規律の不確実性をゼロにする**
- 個別 ADR を 5 本起こすより 1 ADR で文脈共有した方が再読時の見通しが良い
- いずれも「ロール責務の境界」または「ペルソナ採用フロー」に関わる組織規律で、テーマが揃う

### 1.3 PM 起案ルートでの本 ADR の位置付け

ADR-0006 §5.1 で「ペルソナ起案 = PM 主導」が正規化されたが、本 ADR は **ペルソナ起案ではなく組織規律の確定**。PM 起案範囲は（a）スコープ・期日・受入基準（b）人材ペルソナ起案（c）歴史化メモ起票 と ADR-0006 §5.2 で確定済。本 ADR は (a) と (b) の中間にある「組織規律 ADR」を PM が起案する正当性を含めて規律化する（§2.6 で言及）。

## 2. Decision（決定）

### 2.1 論点 1: Designer × FE の境界

#### 採用案: 「数値仕様 = Designer / コンポーネント実装 = FE / 状態遷移フィードバックは共同議論」

| 項目 | 担当 |
|------|------|
| padding / grid / typography / color / 余白の **数値確定** | Designer |
| Squint test / Optical center / 視覚的重心の判断 | Designer |
| React コンポーネント設計（責務分割 / state shape / props 型） | FE |
| ルーティング / データ取得 / 状態管理ライブラリ選定 | FE（Tech Lead レビュー必須） |
| ローディング / エラー / 空状態 の UX | **共同議論（informal 議論）** → 数値仕様が必要なら Designer 確定、振る舞いが主なら FE 確定 |
| アニメーション / マイクロインタラクション | Designer 仕様 → FE 実装 |
| フォントサイズ / line-height の最終値 | Designer |
| アクセシビリティ（WCAG / フォーカス制御 / キーボード対応） | **共同議論** → 機能要件は FE、視覚要件は Designer |

**境界の原則**: 「**見た目の数値**は Designer、**振る舞いの実装**は FE。両者が交わる UX フィードバックは informal 議論で先に言語化してから分業」。

#### 却下案 1A: Designer = 全 UX 確定 / FE = 純実装（裁量ゼロ）

- **却下理由 1**: FE が状態遷移の振る舞い（race condition / optimistic update / ストリーミング表示）を実装する際に Designer の事前指示なしで判断できないと、実装ループが極端に遅くなる
- **却下理由 2**: ローディング / エラー UX は実装制約（API レイテンシ / エラー型）と密接で、Designer が単独で確定すると実装不可能な仕様が出やすい
- **再考の閾値**: FE が UX 仕様を裁量で確定して **Designer から差し戻し 3 件以上連続** で発生した場合 → FE 裁量を縮小し Designer 全権モデルへ移行検討

#### 却下案 1B: FE = UX 込み確定 / Designer = ブランドガイドラインのみ

- **却下理由 1**: ADR-0006 で Designer 採択した理由（PM が UI/UX 良し悪しを単独裁量できないという TASK-0007 失態）と矛盾。Designer 起用の意義を消す
- **却下理由 2**: ブランドガイドラインだけでは具体スライド / 画面レベルでの padding 対称性等を判断できない（TASK-0007 で実証済）
- **再考の閾値**: Designer が業務に対し稼働率 20% 未満の状態が 3 ヶ月続いた場合 → Designer の責務を縮小し FE 裁量モデル検討

### 2.2 論点 2: ADR-0002 §1.1「上限 3 職種」の見直し

#### 採用案: 上限を「**同時進行中タスク数 + 1 を超えない人材数** + 機能的判断」に再定義

ADR-0002 §1.1 の硬い「3 職種」上限を撤廃し、以下のソフト基準に置き換える:

1. **同時進行中 P1 タスク数 + 1** を人材数の上限の目安にする（並列 P0 を避ける PM 原則 §5.6 を機能的に表現）
2. ただし **「ドメイン専門性で代替不能」な職種**（Designer の UI/UX / SRE のインフラ）は同時進行タスク数とは独立に必要時起用可
3. 起用可否は ADR-0006 §4「見落とし候補リスト」の適用トリガー成立で判断

これにより POC 期は **PM + Tech Lead + Designer + BE = 4 職種** が現実解として成立する（同時進行 P1 タスクは通常 1-2 件のため 3 職種で足りるが、Designer は UX 専門で代替不能のため 4 職種目）。

#### 却下案 2A: 3 職種厳守

- **却下理由 1**: Designer 採択（ADR-0006）と矛盾。すでに実質 4 職種で運用しており規範違反状態
- **却下理由 2**: ADR-0006 §4「見落とし候補リスト」5 件（TechWriter / Data / Security / i18n / Product Designer）の適用トリガー成立時に既存 3 職種の入替が必要になり、判断負荷が高い
- **再考の閾値**: チームが 5 名超で意思決定速度が顕著に低下し、PM が「3 職種厳守の方が速い」と判定した場合

#### 却下案 2B: 上限撤廃（無制限）

- **却下理由 1**: PM の意思決定負荷が線形に増える（人材ごとに権限境界・期日・受入基準を維持する必要）
- **却下理由 2**: 「不要な人材を待機させない」という ADR-0002 §1.3 の原則と矛盾
- **再考の閾値**: 同時進行 P0 + P1 タスクが 5 件以上恒常化 / または PM Assistant 起用で意思決定負荷を分散できる体制になった場合

### 2.3 論点 3: PM 起案ペルソナへの Tech Lead レビュー権限（既決の正式化）

#### 採用案: 採択前 Tech Lead レビュー必須

TASK-0011（PR #17 / commit `4beab20`）で運用試行・採用方向で決着済。本 ADR で正式化する:

- PM 起案ペルソナ → Tech Lead レビュー（技術観点 / 運用整合性）→ Tech Lead が squash merge → 採択完了
- Tech Lead レビューは「ペルソナの責任範囲が既存 ADR と整合するか」「技術スキルセット定義に過不足ないか」を観点とする

#### 却下案 3A: PM 起案 → 即マージ（レビューなし）

- **却下理由 1**: PM が技術観点（実装ライブラリ単独裁量 / API 細部）のニュアンスを単独裁量できないリスクを Tech Lead 段階で吸収できなくなる
- **再考の閾値**: PM 起案ペルソナ **5 件連続** で Tech Lead が技術観点の修正提案を出さなかった場合 → informal 確認に降格検討（PM 起案の品質が安定したと判定）

#### 却下案 3B: PM 起案 → Tech Lead 再起案（実質的な共同起案）

- **却下理由 1**: ADR-0006 §5.1 で確定した「PM 起案 = 正規ルート」を実質的に骨抜きにする
- **再考の閾値**: PM 起案ペルソナで採択後に Tech Lead が大改修要求（責任範囲再定義 / 経歴抜本書換）を **2 件以上連続** で出した場合 → 共同起案ルートに戻す

### 2.4 論点 4: `multi-agent-template` の起票タイミング（既決の正式化）

#### 採用案: 後追い派（`mat-notion-watcher` を最初のテンプレ実装にし、`multi-agent-template` は構成抽出として後追い起票）

TASK-0002 受入レビューで PM が採用済。本 ADR で正式化:

- BE 久遠周は `mat-notion-watcher` を最初のサブリポとして **テンプレ実装の品質基準を満たすように丁寧に作る**
- サブリポ 2 つ目以降が現れたタイミングで Tech Lead が `multi-agent-template` を ADR-0008（仮）として起案 → 構成抽出
- `mat-notion-watcher` が稼働を始める前に「テンプレ抽出のルール」を Tech Lead が ADR で定義することは妨げない（任意）

#### 却下案 4A: 先（テンプレリポを先に作る）

- **却下理由 1**: テンプレ要件（共通 lint 設定 / CI / 環境変数 / ディレクトリ構成）は実サブリポを 1 つ作る前は仮説に過ぎず、抽象化が早すぎてミスマッチ多発のリスク
- **却下理由 2**: BE 着任後の最初のタスクが「テンプレリポ整備」になり、実装フィードバックが得にくい
- **再考の閾値**: サブリポが 2 つ目で初期化に **3 回以上の手戻り** が発生した場合 → テンプレ先行アプローチに転換

#### 却下案 4B: テンプレリポを永久に作らない

- **却下理由 1**: サブリポ数が増えるとドリフト（lint 設定 / CI 雛形のばらつき）が顕在化し、Tech Lead レビュー負担が線形に増える
- **再考の閾値**: サブリポ **5 つ以上** で「テンプレなしによるドリフト」が顕在化した場合 → 強制的にテンプレ起票

### 2.5 論点 5: send-keys「通知のみ」規律の CI 自動検証（保留方針の明文化）

#### 採用案: phase1 中は **型ガード + payload 正規表現** で十分。CI 検証は別 ADR-0008（仮）候補として保留

ADR-0003 §4.2-4 で `dispatcher` 層に payload 型ガード + 正規表現制限（`^@@notify TASK-NNNN$` 形式）が実装される。phase1 ではこれをコード型レベルで縛る設計で十分とし、規律違反のベストプラクティス CI レベル検証は別 ADR で Tech Lead が必要時起案。

#### 却下案 5A: 即実装（CI で検証）

- **却下理由 1**: phase1 では送信元（`mat-notion-watcher` の `dispatcher`）が単一で、コード型ガードで十分。CI 検証は二重防御
- **却下理由 2**: CI 設計（payload サンプル収集 / mock dispatcher / lint rule 自作）の工数 vs 規律違反リスクの ROI が POC 期では合わない
- **再考の閾値**: send-keys 規律違反が **1 件でも発生** した場合 → 即時 ADR-0008 起案で CI 検証実装

#### 却下案 5B: 永久保留

- **却下理由 1**: 規律違反リスクをコード型ガードのみで永続的に守る前提は楽観的すぎる（将来 dispatcher が複数化する可能性）
- **再考の閾値**: 該当なし（永久保留は採用しない）

### 2.6 PM が組織規律 ADR を起案する正当性の規律化

ADR-0006 §5.2 で確定した PM 責務「(a) スコープ / 期日 / 受入基準 (b) 人材ペルソナ起案 (c) 歴史化メモ起票」のうち、本 ADR は (b) でも (a) でもない **「ロール責務の境界」「ペルソナ採用フロー」** という第 4 のカテゴリに該当する。

本 ADR でこの第 4 カテゴリを **「組織規律 ADR」** と命名し、PM 起案を正規ルートに含める:

- **対象**: ロール間の責務境界 / ペルソナ採用フローの規律 / 同時進行職種数の上限 / その他「人材を増やす / 縮小する / 責務を変える」判断
- **起案ルート**: PM 起案 → Tech Lead レビュー（採択前必須 / §2.3 と同基準）→ マージ
- **PM 越権の境界**: 組織規律 ADR の中で **技術詳細（実装方式 / CI 設計）まで踏み込まない**。技術詳細は Tech Lead 起案の別 ADR に逃がす（本 ADR §2.5 の send-keys CI 検証はこの原則の実例）

## 3. Considered Alternatives（却下した上位構造の代替案）

### 却下 X: 5 論点を 5 本の独立 ADR で起こす

- **却下理由 1**: 論点ごとの再考閾値が他論点に依存しており、5 本に分けると相互参照が増えて再読時の見通しが悪い（例: §2.2 上限見直しと §2.1 Designer × FE 境界は同じ「ロール拡張時の規律」テーマ）
- **却下理由 2**: 起案 / レビュー / マージのオーバーヘッドが 5 倍になる
- **再考の閾値**: 統合 ADR が 600 行を超えて見通しが悪化した場合 / または特定論点が他論点と独立進化する兆候が見えた場合

### 却下 Y: 全論点を「保留」で次に流す

- **却下理由 1**: BE 着任 + FE 起用判断接近のタイミングで未決を残すと、現場判断で各論点が暗黙確定し ADR と現実が乖離する
- **却下理由 2**: ADR-0006 / ADR-0003 の「開いている論点」が累積し続けるとレビュー時の認知負荷が線形に増える
- **再考の閾値**: 該当なし（保留は本 ADR 採択で却下確定）

### 却下 Z: 統合 ADR は組まず ADR-0006 / ADR-0003 を直接更新

- **却下理由 1**: 既存 ADR の「開いている論点」を直接書き換えると、後追いで読む人が「いつ何が決まったか」を追えない（§Open Questions が決議されたかどうかの履歴が残らない）
- **却下理由 2**: 複数 ADR にまたがる統合判断が記述しにくい（§2.6 PM 組織規律 ADR の正当性のような横断テーマが収まる場所がない）
- **再考の閾値**: 該当なし

## 4. Consequences（帰結）

### 4.1 ポジティブ

1. **BE/FE 採用判断前の組織規律確定** — 5 論点が同時に正式化され、現場判断による暗黙確定リスクがなくなる
2. **PM 起案範囲の明文化** — 「組織規律 ADR」の概念が確立し、PM が技術詳細に踏み込まない境界が明示される（§2.6）
3. **Designer × FE 境界の予防的合意** — FE 起用前に境界が確定するため、起用後の TASK-0007 型失態の予防になる
4. **TASK-0011 / TASK-0002 既決事項の正式化** — 運用試行で得た知見が「仮運用」のまま残らず ADR で固定化される

### 4.2 ネガティブ・リスク

1. **5 論点統合 ADR の保守負荷** — 各論点が独立進化したとき本 ADR の整合性維持が大変
   - **緩和策**: 各論点の再考閾値が異なるため、閾値到達した論点だけ別 ADR で上書きする運用（ADR-0006 の Superseded 粒度明示と同パターン）
2. **PM 越権リスク** — §2.6「組織規律 ADR は PM 起案」を建付けたことで、PM が技術詳細に踏み込む誘惑
   - **緩和策**: §2.6 末尾「技術詳細は Tech Lead 起案の別 ADR に逃がす」を Tech Lead レビュー時のチェック項目化（次回 chore PR で `docs/templates/checklists/pm-self-review.md` に追記）
3. **Designer 採用稼働率の低位安定** — §2.1 採用案で Designer の責務範囲が pptx 系 + Web UI 系に確定。Web UI タスク到来までは pptx 系のみで稼働率が低い可能性
   - **緩和策**: §2.1 却下案 1B 再考閾値「稼働率 20% 未満が 3 ヶ月」をモニタリング。稼働率の計測方法（受領者 = Designer のメッセージ件数 / 全件）を `docs/templates/checklists/pm-self-review.md` 工程 D に追加可能

### 4.3 影響範囲

- **本リポ**: 本 ADR + 後続歴史化メモのみ
- **既存 ADR**: ADR-0006 / ADR-0003 の §「開いている論点」のうち本 ADR 対象論点に「※ ADR-0007 §X で決議」脚注を追加（マージ時に Tech Lead が実施 / または別 chore PR）
- **既存ペルソナ**: `docs/personas/ui_ux_designer.md` §5.4 / `docs/personas/backend_engineer.md` §5 に Designer × FE 境界 / 上限 3 職種見直しを脚注で参照可能（任意 / 次回 chore PR）
- **`docs/templates/checklists/pm-self-review.md`**: §2.6 PM 組織規律 ADR の越権チェック項目を追加（次回 chore PR）

## 5. 開いている論点（PM 承認・議論で動かしたい点）

> 「**強い意見を弱い保持で**」。本 ADR 採択後も議論で動く可能性のある点を明示する。

1. **§2.1 共同議論項目の運用** — 「ローディング / エラー UX」「アクセシビリティ」を informal 議論で言語化する想定だが、実際に FE 起用後にこの議論が機能するかは未検証。FE 着任後 1 ヶ月で再評価
2. **§2.2 ソフト基準の運用** — 「同時進行 P1 タスク数 + 1」を上限の目安としたが、POC 期は同時進行が変動するため目安の解像度が低い可能性。半年後（2026-10-27 頃）に実測値で見直し
3. **§2.3 PM 起案ペルソナの Tech Lead レビュー観点リスト** — 本 ADR では「責任範囲整合 / 技術スキル過不足」と概括したが、観点を `docs/templates/checklists/` に詳細化するかは別議論
4. **§2.4 テンプレ抽出ルールの先行 ADR** — Tech Lead が `mat-notion-watcher` 稼働前に「テンプレ抽出のルール」を ADR-0008 として起案するか否かは Tech Lead 裁量
5. **§2.6 「組織規律 ADR」のカタログ化** — PM が今後起案する組織規律 ADR の累積で「規律のパッチワーク」化するリスク。半年に 1 回統合 ADR で Superseded 化するか、それとも累積を許容するかは別議論
