# TASK-0005 通信プロトコル改訂（カンバン → ハイブリッド型）

- 起票日 / 完遂日: 2026-04-26
- 主担当: Tech Lead 早瀬蒼（起案・PR）/ PM 神崎玲奈（受入承認・マージ・DB スキーマ実装）
- 採択 ADR: [ADR-0005](../adr/0005-communication-protocol-revision.md)
- マージ済 PR: [#13](https://github.com/diesel141/multi-agent-team/pull/13)（commit `e9f20ed`）

## 1. 背景と転換点

本プロジェクトは初期セッション（2026-04-25）で PM 神崎が `CLAUDE.md` §1.3 / `docs/persona.md` §5.1 に **「Notion 掲示板に投稿する業務通信は 3 種メッセージ（開始指令 / 問題報告 / 完了報告）のみ」** と規律化していた。

設計動機は (1) タスクトレーサビリティ確保 / (2) 歴史化単位の純度維持 / (3) 沈黙によるリスク隠蔽の防止 の 3 点だったが、TASK-0001〜0004 の運用実証で次の哲学衝突が顕在化:

| タスク | 摩擦 |
|--------|------|
| TASK-0001 | 完了報告に至るまで Tech Lead 側の状態が掲示板に現れない |
| TASK-0002 | 「中断します」を伝える正規メッセージ種別が無い |
| TASK-0003 | 「速攻なのにカンバン作業で 6 分」「着手返答が投稿できない」とユーザーから直接指摘 |
| TASK-0004 | 設計判断の中間共有（カラー選定理由など）を残す場が無く、完了報告に詰め込み |

ユーザー（プロジェクトオーナー）の初期想定は **Slack/IM 的なフロー型「指示 → 着手返答 → 作業報告」** だったため、PM の初期設計が **越権** していたことが判明。2026-04-26 セッションでユーザーが **案 C ハイブリッド型** を採決。

## 2. 採択した設計（決定事項）

### 2.1 ハイブリッド型 2 層構造

| 層 | 種別 | 必須項目 | 投稿の重さ |
|----|------|---------|-----------|
| **formal** | 開始指令 / 問題報告 / 完了報告 | 既存の必須項目維持 | 重い（規律維持） |
| **informal** | 着手返答 / 進捗共有 / 質疑応答 / 議論 | タスクID / 親タスクID（議論は空可） | 軽い（自由文体可） |

### 2.2 ADR §3.1 計量比較 — 案 (a) 採用

「種別」プロパティを **新オプション追加（必須維持）** とするか **任意化** とするかを 6 軸（DB スキーマ整合性 / 投稿コスト / フィルタ可能性 / 歴史化トリアージ / 拡張性 / 学習コスト）で計量比較。投稿コスト差は 1〜2 秒で実質無視できる一方、フィルタ可能性・歴史化トリアージ・将来拡張性のすべてで案 (a) が優位。「**軽さのために構造を捨てる**」誘惑に抗する判断。

### 2.3 着手返答とステータス遷移の同期化

ADR §2.5: **「着手返答」を投稿した時点で受領者は親タスクのステータスを `未着手 → 進行中` に遷移させる**。informal 4 種は親 formal のステータスを継承する形で運用。これにより掲示板の状態と DB ステータスの乖離を防ぐ。

## 3. ハウススタイルの反転

ADR-0001 / ADR-0002 では **却下案ごとの「再考の閾値」** が 6 箇所漏れていた（`docs/history/2026-04-26_task-0001-acceptance-decisions.md` §6 で記録）。本 ADR-0005 ではこの教訓を踏まえ、**却下案 6 件（A〜F）すべてに測定可能な再考の閾値を埋め込んだ**。

| 却下案 | 再考の閾値（要約） |
|--------|------------------|
| A 現状維持 | informal ノイズ判定 50% / トリアージ 30 分超 |
| B 全面フロー化 | 受入照合 30 分超 / formal 投稿率 20% 未満 |
| C 別 DB 分離 | 単一 DB 500 件超 |
| D コメント機能で吸収 | タスクあたり informal 5 件未満 |
| E 種別任意化 | 3 セッション連続誤分類 |
| F 質疑応答と議論を統合 | 1 ヶ月で境界判定 5 件以上曖昧化 |

「漏れは merge ブロッカー」という TASK-0002 と同水準の品質基準を、本タスクで初回適用した。

## 5. 学びと再現可能な原則

### 5.1 通信プロトコル改訂は 3 点同時改訂が必要

ADR 本体だけでは運用に乗らない。**(1) ADR / (2) 規律ドキュメント（CLAUDE.md / persona） / (3) DB スキーマ実装** の 3 点を同時に動かさないと整合性が崩れる。本タスクでは PR で (1)(2) を、PM 後追いで (3) を実装する分業で対応。

### 5.2 PM の初期設計は越権しやすい

「3 種限定」は PM が「規律徹底」「ノイズ排除」「歴史化純度」を優先して引いた線だったが、ユーザーの素朴な初期想定（フロー型）から逸脱していた。**初期セッションで PM が独断で規約化したものは、後で運用実証 → ユーザー指摘 → 改訂のサイクルが必要**。次回以降の規約起案時は、ユーザーの素朴な想定を先に確認する習慣を持つ。

### 5.3 「軽さのために構造を捨てる」誘惑への耐性

§3.1 計量比較で「種別」を任意化（投稿コスト 0 秒）にしたい誘惑があったが、フィルタ可能性・歴史化トリアージ・将来拡張性のすべてで劣後すると判明。**短期の軽量化が長期の保守コストを増やす設計**は規律で押し戻す。

### 5.4 ハウススタイル違反の反転は次タスクで「100% 適用」

ADR-0001/0002 の漏れ 6 箇所を反省として、本 ADR で却下案 6 件すべてに閾値を入れた。漏れゼロを `merge ブロッカー級` の品質基準として運用に乗せる方針。

## 6. 残課題と昇格対象（PM 18:00 リチュアルでトリアージ）

### 6.1 informal 運用の実証期間

ハイブリッド運用 2 週間の実証を経て、各却下案の再考の閾値（A: ノイズ 50% / B: 受入照合 30 分 / C: DB 500 件 / D: タスクあたり 5 件未満 / E: 3 セッション連続誤分類 / F: 1 ヶ月 5 件曖昧化）を点検する。

### 6.2 §5 開いている論点 5 件

ADR §5 に列挙した 5 件は本 ADR では決め切らず、初回の運用シグナルで判定する:
1. informal をコメント機能で賄うか / 独立ページか（1 週間で議論 5 件溜まったら判定）
2. 議論 → ADR / 歴史化メモへの昇格トリガー（暫定 (iii) 運用ルールのみ）
3. 受領者・発信者プロパティの粒度調整（暫定 (b) 任意化）
4. 進捗共有の頻度上限（暫定 (ii) 運用原則のみ）
5. 着手返答 SLA と未投稿時の扱い（暫定: 30 分努力目標）

- TASK-0002（BE ペルソナ + 通知レイヤ ADR / P1 中断中）の復帰指令を発出
- 復帰指令は Notion 掲示板で「進捗共有」種別の informal 投稿として軽量に行うか、開始指令の補足コメントとするかを実証
