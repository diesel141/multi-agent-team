# 次メンバー提案（ADR-0002 起案）

## 1. 背景

TASK-0001 の成果物 2 として、ADR-0002 (`docs/adr/0002-next-team-members.md`) で
次にアサインする職種の優先順位を起案した。本歴史メモはその意思決定の **要点と
判断軸**を pptx レポート用に圧縮して残すもの。

PM 神崎の「次メンバー選定は Tech Lead に委譲」(`docs/history/2026-04-25_tech-lead-activation-decisions.md` §2.4)
を実運用に落とす最初の決定。

## 2. 採用の幹（Trunk decisions）

| 優先 | 職種 | 起用タイミング | 一行根拠 |
|------|------|---------------|---------|
| 1 | Backend Engineer | **即時** | 通知レイヤと共通 API 雛形が後続全タスクの律速。Tech Lead を「流れを作る」役割に戻す |
| 2 | Frontend Engineer | タスク到来時 | Web UI 案件が来たタイミング。先行起用は待機リソースを生む |
| 3 | SRE / DevOps | タスク到来時 | SaaS 中心スタックで初期は不要。トリガ条件 3 つを明示 |

上限 3 職種は TASK-0001 の受入条件であると同時に、PM の意思決定負荷を抑える
規律でもある（PM ペルソナ §4 明示性 / §5.6 並列 P0 禁止）。

## 3. 重要な却下と「再考の閾値」

| 却下案 | 却下理由（要約） | 再考の閾値 |
|--------|-----------------|------------|
| Mobile Engineer を上位 3 | 直近の Mobile タスク不在 / iOS/Android 別人材で枠を圧迫 | Mobile 開始指令 1 件発行で ADR-0006 起案 |
| QA Engineer を上位 3 | 実装者が Vitest/Playwright 書く方が早い / 待機リスク | リグレッション 1 スプリント 2 件以上 |
| TechWriter を即時 | 研修資料タスク未到来 / 内部ドキュメントは Tech Lead/PM 直書き | 外部公開研修・顧客向け技術ドキュメント発行時 |
| Researcher を即時 | 現時点で継続的リサーチ対象なし | 特定ドメイン継続調査が必要と判明時 |
| SRE を優先 1（即時） | SaaS 中心で運用負荷低 / Conway's Law で過剰 | サブリポ 3 以上 or 月額 $200 超 or 本番障害 1 件 |
| PM Assistant / Scrum Master | PM 神崎が情報設計を自前担保 / 3 種メッセージ規約で儀式不要 | （該当なし） |
| 上限 3 を緩めて 4 以上一括 | TASK-0001 受入条件違反 / PM 意思決定品質低下 | （該当なし） |

却下案ごとに **測定可能な再考閾値**を持たせることで、後続 Tech Lead が「いつ
ペルソナを追加すべきか」をルール化できる。

## 4. 設計原則の埋め込み

ADR-0002 は以下を反映している:

- **Conway's Law**（Tech Lead ペルソナ §8）— 通信レイヤの実装担当者がいないと
  アーキテクチャが机上に留まる → BE 即時化の根拠
- **少数精鋭** — 待機メンバーを作らない（FE/SRE をトリガ式に）
- **明示性**（PM ペルソナ §4）— トリガ条件を測定可能な形で記述
  （「Web UI を含む開始指令」「月額 $200 超」「本番障害 1 件」）
- **強い意見を弱い保持で**（Tech Lead ペルソナ §10）— §5「開いている論点 4 件」で
  PM が動かせる余地を明示

## 5. 後続フローの起動

ADR-0002 が PM 承認されたら、以下の順で動く:

1. ADR-0003: Backend Engineer ペルソナ起案（Tech Lead）
2. PM が承認したら Notion 掲示板に「TASK-0002 BE 起用」開始指令を発行
3. BE 着任 → 通知レイヤ実装 / テンプレートリポ整備 / 共通 API 雛形に着手
4. FE/SRE のトリガ条件が成立した時点で ADR-0004 / ADR-0005 を起案

## 6. リスクと緩和策（要点）

| リスク | 緩和策 |
|-------|--------|
| BE 着任時の TASK-0002 で品質が決まる | PM/Tech Lead 共同で受入基準をレビュー |
| 「タスク到来時」が先送りの口実になる | トリガ条件を §2.2 で測定可能な形に明示 |
| 3 職種上限の窮屈さ | 却下案ごとの再考閾値で動的に入替可能 |

## 7. なぜこれを残すか（歴史化の理由）

1. **Tech Lead に委譲された判断の最初の発動**として、本プロジェクトのチーム拡張
   プロセスを規定する。今後のメンバー追加判断のテンプレになる
2. **却下案と再考閾値の組** が「いつ何を見直すか」を Tech Lead 横断で共有でき、
   後続 Tech Lead が同じ議論を最初からやらずに済む
3. **PM/Tech Lead の責任分担**（PM = 期日・スコープ、Tech Lead = 技術と人材判断）の
   運用例として、pptx レポートの「Phase 1: チーム構築」章の中核資料となる
