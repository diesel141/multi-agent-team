🎓 主要な知見と教訓

1. IDE 統合パスの選定

Antigravity IDE のネイティブ機能では LM Studio との直接統合が困難でしたが、Continue 拡張機能を使用することで実現できました。

2. Continue の設定ファイル形式

Continue の設定は YAML 形式（config.yaml）であり、JSON ではありません。モデル識別子は完全形式（qwen/qwen2.5-coder-14b）で指定する必要があります。

3. GPU メモリの効率的な活用

RX-6900XT の 16GB VRAM に対して、Q4_K_M 量子化された 14B モデルを 78.9% の利用率で運用でき、十分な安全マージン（21.1%）を確保できます。

4. Antigravity + Continue でのローカルLLM利用の限界

Antigravity + Continue でのローカルLLM利用は、推論ばかり肥大し、簡易なコーディングタスクには不向きと感じました。

📝 総評

アプリ開発におけるローカルLLMの実用性

  • 検索・コーディング・テストといった単機能タスクであれば、2B クラスの小型モデル（granite-3.3-2b 系）でも十分実用に耐える
  • 設計～実装まで通しで任せる場合は、モデル性能と応答速度のバランスが重要（現環境では granite-4.0-h-tiny が最適解）
  • 8B 超のモデルはフリーズやオフロード負荷が顕著になり、16GB VRAM 環境では実用性が急激に低下する
  • IDE 統合（Antigravity＋Continue）は推論が肥大しやすく簡易タスクに不向き。CLI 経由の利用の方が軽快に運用できる

クラウドLLMとの比較（速度・性能）

  • 純粋な推論性能（コード品質・複雑なタスクの遂行能力）は、クラウドの最新大型モデルには及ばない
  • ネットワーク遅延・onピーク時の混雑がないため、自動補完などの短い応答はローカルの方が体感が安定する
  • API 利用料・レート制限が一切なく、試行錯誤を無制限に回せる点はクラウドにない強み
  • 長文コンテキストや高負荷タスクではロード時間・推論時間が顕著に伸び、クラウドとの性能差が大きく開く

ローカルLLMを利用すべきシーン

  • 機密性の高いコード・データを外部に出せない案件（データプライバシー要件がある開発）
  • 自動補完・コミットメッセージ生成など、小さな推論を高頻度で回すタスク
  • オフライン環境やネットワークが不安定な環境での開発
  • API コストを気にせず大量の試行錯誤（プロンプト検証・テスト生成など）を行いたい場合
